# 量化系统架构原则：后端计算与前端展示的分离

## 1. 核心原则：Strategy-Driven Architecture (策略驱动架构)

在专业的量化交易系统中，**策略逻辑（后端）与可视化展示（前端）必须严格解耦**。

**黄金法则**：
> **"策略永远只信任自己计算的数据。图表只是数据的观察者，绝非数据的生产者。"**

---

## 2. 为什么不能依赖前端图表计算指标？

如果让前端图表控件（如 TradingView TA Charts）计算指标，并将其传回后端用于交易，会产生以下致命风险：

### 2.1 运行时依赖风险 (Availability Risk)
*   **浏览器限制**：前端计算依赖于用户打开浏览器网页。如果网页关闭、卡顿或网络中断，前端计算就会停止。
*   **无人值守需求**：量化机器人通常部署在云服务器上，需要 7x24 小时在后台静默运行（Headless），根本没有浏览器环境来渲染图表。

### 2.2 数据一致性风险 (Consistency Risk)
*   **算法差异**：虽然指标名称相同（如 EMA），但不同库的实现细节可能不同。
    *   *前端 (JS)*: 可能使用简单的递归算法。
    *   *后端 (Python/Pandas)*: 可能使用 `ewm(adjust=False)` 或 `adjust=True`。
    *   *结果*：数值可能相差 0.01，导致前端看到金叉，后端策略却判断未金叉，从而产生“幽灵交易”或漏单。
*   **数据窗口差异**：
    *   前端为了加载速度，可能只加载最近 1000 根 K 线。
    *   后端策略可能加载了最近 1 年的数据。
    *   对于依赖历史数据的指标（如 EMA, MACD），初始数据的不同会导致后续所有计算结果的微小偏差（Cold Start Problem）。

### 2.3 延迟风险 (Latency Risk)
*   **通信往返**：`行情 -> 前端接收 -> 前端计算 -> 发送给后端 -> 后端下单`。这比 `行情 -> 后端计算 -> 后端下单` 多了两次网络传输和一次浏览器渲染开销，增加了数百毫秒的延迟。

## 3. 正确的架构模式：Backend Calculation (后端计算)

我们在本项目中采用的是标准的机构级架构：

### 3.1 数据流向
1.  **行情源** (Binance/CCXT) 推送数据到 **后端 (Python)**。
2.  **后端** 使用统一的计算库 (Pandas / TA-Lib) 计算所有技术指标。
3.  **后端** 根据计算结果执行交易逻辑 (Signal Generation & Execution)。
4.  **后端** 将计算好的指标数据（K线 + 指标线）通过 API/WebSocket 推送给 **前端**。
5.  **前端** (React + Lightweight Charts) 仅负责将接收到的数据**画**在屏幕上。

### 3.2 优势
*   **单一事实来源 (SSOT)**：图表上看到的指标数值，就是策略实际使用的数值，分毫不差。
*   **高性能**：Python 的科学计算库 (`numpy`) 处理百万行数据比 JS 快得多。
*   **稳定性**：即使前端页面崩溃或关闭，后端的交易逻辑依然在稳定运行。

---

## 4. 扩展性指南：如何增加新指标？

在此架构下，增加新指标的标准流程如下：

1.  **Python 侧 (生产者)**：
    *   在 `src/utils/data_helper.py` 中实现该指标的计算逻辑（使用 pandas/numpy）。
    *   在 API 接口中暴露该指标的参数配置。

2.  **React 侧 (消费者)**：
    *   在 `ChartWidget.tsx` 的菜单中增加选项。
    *   向后端请求该指标数据。
    *   使用 `addLineSeries` 或 `addHistogramSeries` 将数据可视化。
